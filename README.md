## Установка

Для первичного запуска необходимо создать `.env` файл, содержащий настройки программы. К примеру, URL базы данных.

```sh
cp .env.example .env
```

uv run api

### Подчёркивания в названиях некоторых файлов

Так в Python принято обозначать файлы, в которые не положено заглядывать сторонним пользователям кода. 
По сути, просто соглашение, а трактую его я как невозможность импортировать из этого файла из других модулей.

Если требуется какой-то класс или переменная из этого файла, 
то в `__init__.py` текущего модуля будет её импорт и проброс в `__all__`.

### Защищённые методы

Я не стал использовать приватные методы (`__method_name`), 
ограничился защищёнными (с одним подчёркиванием: `_method_name`). 

Такие методы автоматически не попадают в `__all__`, но помимо этого всем своим видом показывают, 
что не являются чем-то для использования из внешних модулей. 

С приватными методами, кстати, в рантайме происходит name mangling, 
имя с `__method_name` будет заменено на `_ClassName__method_name`. 
Вне класса такой трюк не сработает, mangling произведён не будет.

По сути причина такая же, как и у прошлого пункта.

## Что я сделал бы иначе?

Во первых, я бы переименовал в модели `BookingOut` несколько полей:

- `name` -> `guest_name`
- `phone` -> `guest_phone`

А также фильтр по дате в ручке `GET /bookings`: `date` -> `booking_date`.

Так получится решить возможное недопонимание, так как телефон, например, 
может принадлежать не гостю заведения, а оператору, который принимал заявку. 

Также и имя может быть не именем гостя, а именем того же оператора.

По той же причине `date` не даёт достаточно информации, это дата брони или дата, 
когда бронь была произведена (`booked_at_date`).

### Тестрование

Я старался следовать принципам SOLID, но для упрощения реализации не стал выделять интерфейсы некоторых классов. 
Так, например, BookingRepository я бы сделал абстрактным классом (`abc.ABC`), у которого все методы были бы также абстрактными (`abc.abstractmethod`).

А затем при тестировании реализовал бы in-memory модель хранения броней. Так можно было бы отдельно тестировать реализации сервиса и репозитория.

Таким же образом можно поступить и с сервисом, тогда ручки можно будет тестировать, мокнув сервис. 
Однако здесь пришлось бы решить проблему конвертации внутренней модели репозитория во внешнюю схему, которая выдаётся из ручки. 
Скорее всего я:
а) либо воспользовался бы протоколами со всеми нужными полями. 
б) либо сделал репозиторий и сервис Generic, 
   требовал бы реализации защищённого метода 
    ```python

    import abc

    class AbstractBookingService[M, R](ABC, BookingService[R]):
        # Здесь override методы интерфейса BookingService, которые используют 
        # _booking_model_to_out, чтобы преобразовать результаты из Repository.
        ...

        @classmethod
        @abc.abstractmethod
        def _booking_model_to_out(cls, model: M) -> R`.
    ```
